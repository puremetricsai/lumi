# TCC spike — what an ad-hoc signature costs

**Date:** 2026-08-17
**Question:** When an `.app` bundle spawns the bundled `lumi record start --foreground` as a
directly-held child, does TCC hold the *app bundle* responsible? And what happens to those
grants when the bundle is rebuilt without a Developer ID signature?
**Answer:** Attribution works exactly as the architecture doc assumed — a full capture ran
under the bundle, with Accessibility attribution intact. Persistence does not. Every
rebuild, including a rebuild of the Go binary alone, stops every grant the app had earned
from applying, and Screen Recording and Accessibility then cost a manual trip to System
Settings to restore. The *row* in System Settings can outlive the identity that earned it —
see Result 5 — which is why "the grant is gone" and "the toggle is off" are not the same
statement.

This is the spike `docs/research/2026-08-01-mac-desktop-app-architecture.md` asked for.

## Method

A throwaway bundle, `LumiTCCSpike.app`, bundle id `dev.lumi.tccspike`, deliberately *not*
the identifier the shipped app will use, so the experiment cannot poison the real app's TCC
record. It contains a small AppKit executable and a copy of the repo's `lumi` binary at
`Contents/MacOS/lumi`. Both are ad-hoc signed (`codesign --force --sign -`). It is launched
with `open -a`, never from the terminal, so LaunchServices — not the shell — is its parent.

It runs these phases as directly-held child processes, logging to `/tmp/lumi-tcc-spike.log`:

1. `lumi permissions` — status before anything is requested.
2. `lumi permissions --request` — the request flows.
3. Hold open, polling `lumi permissions` every 5s, waiting for Screen Recording and
   Accessibility.
4. `lumi record start --foreground --duration 12s` — a real bounded capture.
5. `lumi permissions` — status after.

Environment: macOS 26.5.2 (25F84), Apple Silicon, Swift 6.3.3 / Xcode 26.6.

## Result 1 — attribution works. The bundle gets its own TCC identity.

The same `lumi` binary reports opposite answers depending on who launched it.

From the terminal, where every permission has been granted for months:

```
Screen Recording    granted
Accessibility       granted
Input Monitoring    granted
Microphone          granted
Speech Recognition  granted
```

From inside `LumiTCCSpike.app`, first launch, phase 1:

```
Screen Recording    denied_or_not_determined
Accessibility       denied_or_not_determined
Input Monitoring    not_determined
Microphone          not_determined
Speech Recognition  not_determined
```

The child inherited **nothing** from the terminal. TCC resolved the responsible process to
the app bundle, which is the property the whole two-artifact design depends on. A foreground
child, held by the app, is attributed to the app.

The negative half matters too: the terminal's existing grants are a separate identity.
Installing the app does not carry them over, and the app cannot borrow them.

## Result 2 — the whole pipeline runs under the bundle

With all five permissions granted to the bundle, phase 4 exited 0:

```
msg="recording started" database=/tmp/lumi-tcc-spike-data/lumi.db screen=true audio=true
msg="captured screen" id=1 display=1 app=UserNotificationCenter text_source=vision characters=1802
msg="captured screen" id=2 display=1 app=Claude                 text_source=vision characters=2836
msg="captured screen" id=3 display=1 app=Zed                    text_source=vision characters=1868
msg="captured screen" id=4 display=1 app=Zed                    text_source=vision characters=1910
msg="captured audio"  id=5 source=system     characters=0 segments=0
msg="captured audio"  id=6 source=microphone characters=0 segments=0
```

ScreenCaptureKit, Vision, and — the one that would have been easy to get wrong —
**Accessibility attribution** all worked from a child of the app bundle.

An app name in the log is not by itself proof of that last point: `internal/capture` will
fill `app` from the NSWorkspace fallback when Accessibility is unavailable, and the log line
does not say which path produced it. The stored metadata does, and it says Accessibility:

```
$ lumi search --data-dir /tmp/lumi-tcc-spike-data --json
"app_source": "accessibility", "attribution_source": "accessibility",
"accessibility_trusted": true
```

The same query shows the audio rows carrying the failure rather than hiding it:

```
"processor_error": "transcription skipped after capture stopped: context deadline exceeded"
```

Both tracks were written, indexed, and tagged with why they hold no text — `characters=0`
alone would have been indistinguishable from genuine silence. That is the "never lose
captured media" rule behaving correctly, read out of the database rather than assumed.

The best single piece of evidence in this spike is accidental. Frame 1 caught the TCC dialog,
and Lumi's own Accessibility read recorded what it said:

```
"LumiTCCSpike" is requesting to bypass the system private window picker and directly
access your screen and audio.
```

The system dialog named the **app bundle**. Not Terminal, not the shell, not the Go binary.
That is the attribution question answered by the operating system in its own words, and it
also confirms the prompts were real dialogs a person answered.

## Result 3 — an ad-hoc designated requirement is literally the cdhash

```
$ codesign -d -r- LumiTCCSpike.app
# designated => cdhash H"a83829e836ea3b558f76dbfdf56823e546efc7dc"
```

That single line is the whole problem. A Developer ID signed app's designated requirement
names the *identifier and the signing team*, which are stable across builds:

```
identifier "com.example.App" and anchor apple generic and
  certificate leaf[subject.OU] = "TEAMID"
```

An ad-hoc signature has no team and no chain to anchor to, so `codesign` can only pin the
exact bytes. TCC stores that requirement with the grant. Change any sealed content — the
main executable, a nested binary, or anything covered by `CodeResources` — and the stored
requirement no longer describes the app that is asking.

## Result 4 — grants survive a relaunch, and die on a rebuild. Measured.

Same bundle id `dev.lumi.tccspike` throughout. Every row is a **phase 1** reading, taken
before that run issues any request of its own:

| Run | cdhash | What changed since the previous run | Mic | Speech | Screen Rec | Access. | Input Mon. |
| --- | --- | --- | --- | --- | --- | --- | --- |
| A first launch | `a83829e8…` | — | not_det. | not_det. | denied | denied | not_det. |
| B rebuilt shell | `613ddf9c…` | Swift executable rebuilt | **not_det.** | **not_det.** | denied | denied | denied |
| C relaunch, no rebuild | `613ddf9c…` | nothing at all | **granted** | **granted** | denied | denied | denied |
| D Go binary swapped | `4d175bc1…` | only `Contents/MacOS/lumi` replaced | **not_det.** | **not_det.** | denied | denied | denied |
| E after System Settings | `2c5a8a80…` | rebuilt *and* moved to `~/Applications`; then granted by hand | granted | granted | **granted** | **granted** | granted |
| F rebuilt after E | `8931a913…` | Swift executable rebuilt | **not_det.** | **not_det.** | **denied** | **denied** | **denied** |

Reading the table needs one thing it cannot show: each run also ran `lumi permissions
--request` in its own phase 2, and that is what put Microphone and Speech Recognition back to
`granted` within the run. So B's phase 1 reads `not_det.` and C's phase 1 reads `granted`
because **B re-granted them after B's own phase 1 was taken.** The E row is likewise a
phase-1 reading taken after the previous session's manual grants, not a state E created.

Run C is the control that makes the rest mean something: relaunching the *same* build, with
nothing rebuilt in between, keeps the grants. So the losses in B, D and F are caused by the
rebuild, not by quitting the app.

Run F is the complete answer: **all five permissions stop applying after a rebuild**,
including the two that a dialog cannot restore.

**Run D is the finding that actually hurts day to day.** Nothing in the Swift shell changed.
Only the bundled Go binary was replaced and the bundle re-signed — exactly what `task build`
followed by `task app` will do, many times a day, for the whole of this work. The bundle seal
covers nested files, so the app's cdhash moved and every grant went with it.

## Result 5 — a stale entry can read as enabled and still be denied

Observed once, and worth knowing because the symptom is baffling: after several rebuilds,
`LumiTCCSpike` appeared in Screen & System Audio Recording, was toggled **on**, and the app
still read `denied_or_not_determined` — through a full app relaunch. The likeliest
explanation is that the row was left over from an earlier cdhash, so the toggle described an
application that was no longer the one asking; that is a hypothesis, not something this spike
isolated. What *was* observed is the recovery. Running

```sh
tccutil reset ScreenCapture   dev.lumi.tccspike
tccutil reset Accessibility   dev.lumi.tccspike
```

cleared the stale rows; re-enabling in System Settings then worked and the status flipped to
`granted`.

The mechanism was not isolated further, so treat this as an observed recovery procedure
rather than a fully characterized rule. A `tccutil reset` on its own does **not** restore a
grant — it only removes the obstruction; the user still has to re-enable.

### Addendum, 2026-08-27 — the mechanism, measured

The hypothesis above is now confirmed, on a *released* bundle rather than an ad-hoc one:
`com.puremetricsai.lumi` 0.3.1 in `/Applications`, signed `Developer ID Application: Pure LLC
(C34G34593Q)`, sat on the Permissions screen with both rows switched on in System Settings.
`log show --predicate 'process == "tccd"' --info --debug` prints the stored requirement and
why it fails:

```
-[TCCDAccessIdentity matchesCodeRequirement:]: SecStaticCodeCheckValidity() static code
from com.puremetricsai.lumi : identifier "com.puremetricsai.lumi" and
certificate leaf = H"59927e267f2a2d30a44e8c3551340e8207e5e609"; status: -67050
```

The bundle's actual leaf is `9F:01:CB:85:25:0A:E7:6C:1E:11:D0:F3:97:93:4C:9E:BA:07:88:0C`.
`-67050` is `errSecCSReqFailed`. So **TCC pins the leaf certificate, not the designated
requirement** — which narrows the claim in `macos/CLAUDE.md` that a cert-based DR makes grants
"survive an upgrade". They survive an upgrade only while the *certificate* is unchanged; a
renewal, or a move from ad-hoc to Developer ID, is a new identity and every existing grant
stops applying with its switch still on.

Screen Recording failed differently in the same session — `ReqResult(Auth Right: Unknown
(None), promptType: 1, DB Action:None, UpdateVerifierData)`, meaning no record for the bundle
at all, so `CGPreflightScreenCaptureAccess()` returns false and the request flow *can* still
prompt. Accessibility read `Denied (System Set)` after an unprivileged `tccutil reset`,
because that row lives in the system database; clearing it needs `sudo`, or the row removed in
System Settings.

The same trace re-confirms Result 1 on a signed build: `AttributionChain:
responsible={identifier=com.puremetricsai.lumi ... LumiApp}, requesting={identifier=lumi,
binary_path=/Applications/Lumi.app/Contents/MacOS/lumi}`, with Microphone and Speech
Recognition both `Allowed (User Consent)`. Attribution is not what breaks here.

This trace is the cheapest way to tell a stale grant from a real refusal without Full Disk
Access, and it is why the Permissions screen carries the "already looks on" caption
(`macos/Lumi/Sources/LumiWindow.swift`) rather than a branch: the app itself cannot see any
of the above.

## Result 6 — a denial persists where a grant does not

After a rebuild, Microphone and Speech Recognition land on `not_determined`, while Input
Monitoring lands on `denied` (runs B, D and F). Both lost their grant, but only the first two
end in a state that will raise a fresh prompt; a `denied` service does not re-prompt.

Treat a permission that reads `denied` after a rebuild as possibly stale rather than as the
user's settled intent, and always offer the "Open System Settings" path rather than assuming
a re-prompt will appear.

## What this costs, concretely

- **Nothing about the architecture is wrong.** Foreground child + app bundle = correct TCC
  attribution, proven through a real capture. Deliverables 3–6 proceed unchanged.
- **Expect to re-grant after every build during development.** This is not a bug in the app
  and must not be debugged as one. The symptom is always the same shape: permissions that
  worked five minutes ago read `not_determined` or `denied_or_not_determined`, and the Lumi
  window opens in its Permissions state.
- **Screen Recording and Accessibility are the expensive ones.** Microphone and Speech
  Recognition come back with a dialog — two clicks. Those two need System Settings, and
  sometimes a `tccutil reset` first (Result 5).
- **Users would pay the same cost on every app update**, which is the real reason Developer
  ID signing is not optional for shipping. It is deliberately out of scope here (§7 of the
  brief), and this is the measurement that says what deferring it costs: a stable TCC
  identity. Developer ID also carries authenticated provenance and is the precondition for
  notarization and a clean Gatekeeper launch, both deferred alongside it. The app-bundle
  benefit motivating this whole design only fully arrives with a real signature.

### Working procedure while unsigned

1. Keep one bundle at one stable path (`~/Applications/Lumi.app`) and rebuild in place.
   The path is not what TCC keys on, but one path keeps System Settings from accumulating
   one row per copy.
2. After a rebuild, re-enable Screen Recording and Accessibility in System Settings.
3. If the row is toggled on and the app still reads denied, `tccutil reset <service>
   <bundle-id>`, then re-enable. The reset removes the obstruction; it never restores a grant.

One thing this spike did **not** establish, and which should not be assumed: whether a change
picked up in System Settings reaches an already-running app, or needs the app relaunched. In
the one session where it mattered, an app relaunch alone did not help — the `tccutil reset`
did — so no ordering rule here is trustworthy yet. When a grant looks stuck, reset and
re-enable rather than guessing at relaunch order.

### The mitigation this machine cannot use

Signing with an **Apple Development** identity instead of ad-hoc would give the bundle a
designated requirement anchored to a certificate rather than to the bytes, so grants would
survive rebuilds during development without any of the above. It is not available here:

```
$ security find-identity -v -p codesigning
     0 valid identities found
```

Obtaining one is a separate decision with its own setup (an Apple account and a keychain
identity), and it is not what §7 of the brief scoped. Noted because it is the only real
escape from the churn above — otherwise the identity is the hash, and there is no workaround.

## Reproducing

The spike is throwaway and is not checked in. `main.swift` and `build.sh` build the bundle,
ad-hoc sign the nested binary and then the bundle, and print the cdhash:

```sh
codesign --force --sign - "$APP/Contents/MacOS/lumi"
codesign --force --sign - "$APP"
codesign -d -r- "$APP"          # shows the cdhash-only designated requirement
open -a "$APP"                  # never launch it from the shell
cat /tmp/lumi-tcc-spike.log
```

Re-run `build.sh` with a different marker argument to produce a different cdhash and watch
the grants disappear.
